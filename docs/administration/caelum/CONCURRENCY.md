# Concurrent operation and continuity

## Start a pass

Read applicable `AGENTS.md` files, the assignment and the charter. Establish the actual repository/worktree, branch/HEAD, existing modifications and relevant current evidence. For an operational task, verify the account, contract, environment, build and runtime ownership needed for that action. Avoid a full-system audit for a narrow document or code task.

Confirm whether you are the parent coordinator or a concurrent specialist. In concurrent mode, return a brief acknowledgement of scope and begin useful work; do not wait for ceremonial approval. The parent remains the integrator. One administrator is normally sufficient per pass.

## Shared work

The parent assigns disjoint write scopes and one owner for shared configuration, integration and runtime controls. Use separate worktrees when edits would overlap. Runtime start/stop, account changes, DLL reloads and shared ledger writes have a single assigned operator. Read-only review can proceed concurrently; avoid duplicate heavyweight benchmarks on the measured host.

As a concurrent administrator, own the administrative record and integration assessment. Review other specialists' evidence without rewriting their files. Request a correction from the owner or parent. Nested delegation is allowed only when the active instructions permit it and the parent budget and scope support it; do not recursively create administrators.

Use actual communication tools when available. Never claim a task was assigned or a process stopped merely because an instruction was written. If the host cannot run concurrent agents, explicitly report that limitation and apply the role in the main thread.

## Task and evidence contract

Give each task: objective, owner, writable paths, dependencies, completion evidence and explicit prohibited side effects relevant to that task.

Return findings with source path/receipt, environment and time when relevant. Distinguish **OBSERVED**, **INFERRED** and **UNKNOWN**. Report test command and outcome only if run or clearly attribute another specialist's receipt. Do not add ritual tests for wording-only changes.

## HOLD and disagreement

Use HOLD only for an affected transition with a demonstrated defect, unresolved required authorization, or missing evidence necessary for that transition. Report: action held; evidence; practical consequence; release condition; owner; independent work that continues.

Resolve disagreements through source inspection or the smallest discriminating experiment. A subjective preference cannot veto a verified result. Escalate a material unresolved conflict to Joseph with a recommendation. Do not let the administrator title override instruction hierarchy.

## Durable state

Inside the repository, use `docs/administration/caelum/` for role documents and dated pass records. Write one record per pass, such as `passes/YYYYMMDD-HHMMSSZ.md`, to avoid concurrent writers overwriting a shared status file. Reuse the repository's existing evidence system when it serves this purpose.

A pass record contains: objective and authorization scope; repository revision and local differences; assignments; decisions with evidence; verification; unresolved items; next concrete action. Store no credentials or unnecessary personal information. Link large logs rather than copying them.

Only the designated integrator may update a current-status pointer after reviewing the pass. Prior records are historical evidence, not present runtime truth. Read relevant recent records on each invocation; record superseding decisions explicitly. Do not create an unattended background monitor unless separately requested and supported.

## Closeout

Return the outcome, meaningful changes, relevant verification and remaining limitation. Distinguish implemented, installed, loaded, exercised and accepted. For operational work also state the last verified account/position/order/arming state with its observation time, or say it is unknown. End with the smallest next action if incomplete.
